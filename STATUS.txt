JWE3 VR - status log (newest first)
===================================

2026-10-27  0.0.5  In-world HUD without pass markers: the UI leaves the eye images (remote test, headset not worn)
    - How JWE3 composes a frame (runs 19-25): the backbuffer is never a render target (2 barriers, 1 copy per frame);
      the game copies a 1920x1080 R10G10B10A2 image into it, and that image is written by a compute pass (only ever
      UNORDERED_ACCESS <-> COPY_SOURCE). So the old rule "backbuffer bindings are UI" could never fire.
    - New debug aid JWE3VR_rt.req (render-target census): logs one frame's render targets (formats, bindings, the
      state each leaves RENDER_TARGET for) and saves each large one, copied inside the game's own list just before
      it leaves RENDER_TARGET. Run 23: 19 targets; one 1920x1080 RGBA8 sRGB target leaving for COPY_SOURCE holds
      exactly the HUD (toolbar, bottom bar) on transparent black; another is the G-buffer albedo.
    - Trace of those UI textures (run 25): two textures in turn; each frame the UI is drawn into one (bound twice,
      through sRGB and UNORM views) while the other, last frame's, is cleared.
    - New default UIDetect = texture: a frame-sized 8-bit target leaving RENDER_TARGET for COPY_SOURCE is learned as a
      UI texture; its bindings draw into the mod's own (typeless RGBA8, UNORM + sRGB views), and the game's own is
      cleared at that binding so the compositing pass finds no UI. The HUD panel now has its own swapchain in the UI
      texture's format (RGBA8 sRGB, 8-bit alpha) instead of the eyes' 10-bit format (2-bit alpha, and copying
      RGBA8 into it would have been invalid).
    - Run 26 (re/work/run26_pair.png): the eye image has no UI, the HUD texture has the whole UI; "in-world HUD
      active"; no warnings or errors in the log. Not seen: the panel in a worn headset (session never got past
      synchronized), and laser clicks on it.
    - Also in this version (code only, not yet reached in a run): the rig kind follows the UI mode the player enters
      (drive -> first-person vehicle, gunner -> at the gun mount with the body's orientation, photo, guest cam,
      cinematic), because the camera component's mode name is not reachable from the park's Lua state; a run of
      camera ticks reading back only the mod's own writes is counted (run 14 checks: 301 ticks, 0 own reads).

2026-10-27  0.0.4  VR camera drives the rendered frame in a JWE3 park (remote test, headset on the desk, not worn)
    - Found why the camera never ticked: a park shares the startup Lua state (startup globals visible from the
      park), so every hook is in force, but the camera component (CameraModeManager and its mode modules) runs in
      a Lua state the mod cannot reach: neither the manager wrapper nor the 23 mode wrappers is ever called.
    - New camera path (JWE3VR.Camera.ManagerTick): the VR manager's Advance reads the camera transform the game
      produced, uses it as the anchor (never its own previous write), runs the rig and writes SetTransform/SetFOVY.
      Log: "camera tick (manager path): mode Standard, VR override 1.0". The screenshot (re/work/run14_park2.png)
      shows the rig's camera: level horizon, 116 deg FOV, eye at the headset's height; foveation switched on by
      itself ("VRS tier 2 ... rate image for 116 deg FOV"). So the manager runs after the camera component.
    - Also: managers get Advance(dt) only (no unscaled dt) and a paused park passes dt 0; diagnostics count frames.
    - Open: the camera mode name comes from GetWorldAPIs().CameraModeManager only if that is reachable (not yet
      confirmed; defaults to Standard, so walking/vehicles would use the overview rig until this is solved);
      head motion, stereo depth and controllers untested (nobody wore the headset); HUD/TAA pass detection.

          GPU was still using while the game shut down; the game then exited with its own 0xFDEAD fatal path and
          showed a "GPU Driver Crash" dialog on the next start. Fixed: Submit never resets an allocator still in

          Not Sophos: no detections in its logs; SophosED.dll frames were just its API hooks. The crash reporter
          was closed without sending anything.
        * In-park closing: a close request opens a quit dialog; the run scripts now end the process instead.
